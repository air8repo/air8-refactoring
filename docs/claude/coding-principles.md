# 编码行为准则

> 用于减少常见 LLM 编码错误的行为准则，与项目规范（TDD、spec 流程）配合使用。
> 权衡说明：这些准则偏向谨慎而非速度。对琐碎任务，自行判断把握尺度。

## 1. 先思考，再写代码

不要假设。不要隐藏困惑。主动暴露权衡。

动手实现之前：

- 明确说出你的假设。不确定就问。
- 存在多种理解时，把它们摆出来——不要默默选一种。
- 存在更简单的方案时，说出来。该反驳时就反驳。
- 有不清楚的地方就停下来，指出困惑点，提问。

## 2. 简单优先

用解决问题的最少代码。不写任何投机性的东西。

- 不做超出要求的功能。
- 不为一次性代码建抽象。
- 不加没人要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景写错误处理。
- 写了 200 行但 50 行能解决的，重写。

自问："资深工程师会不会说这写复杂了？"会，就简化。

## 3. 外科手术式修改

只动必须动的。只清理自己制造的垃圾。

修改现有代码时：

- 不"顺手改进"相邻的代码、注释或格式。
- 不重构没坏的东西。
- 遵循现有风格，即使你有不同偏好。
- 发现无关的死代码，提一句——但不要删。

你的修改产生孤儿时：

- 删除**因你的修改**而不再使用的 import / 变量 / 函数。
- 不删除既有的死代码，除非被要求。

检验标准：每一行改动都能直接追溯到用户的请求。

## 4. 目标驱动执行

定义成功标准，循环直到验证通过。

把任务转化为可验证的目标（与本项目 TDD / EARS 验收标准天然衔接）：

- "加校验" → "先为非法输入写测试，再让测试通过"
- "修 bug" → "先写一个能复现它的测试，再让测试通过"
- "重构 X" → "确保重构前后测试都通过"

多步任务先列简短计划：

```
1. [步骤] → 验证：[检查方式]
2. [步骤] → 验证：[检查方式]
3. [步骤] → 验证：[检查方式]
```

强的成功标准让你能独立循环推进；弱的标准（"让它能跑"）会导致反复找人澄清。

## 生效的标志

这些准则起作用的表现：diff 里不必要的改动更少、因过度复杂导致的返工更少、澄清性提问发生在动手之前而不是犯错之后。
